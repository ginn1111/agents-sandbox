# The Hermes dashboard Portal gets a generated login, and every Workspace gets its own Kanban home

The Hermes dashboard is a built-in Portal entry (ADR-0010): `hermes dashboard --host 0.0.0.0 --port 9119 --no-open`, started by the CLI when the user runs `asb portal start hermes-dashboard` (ADR-0013). Because it listens on a non-loopback address, Hermes refuses to start without a login, so the entry's `HERMES_DASHBOARD_BASIC_AUTH_USERNAME`, `_PASSWORD` and `_SECRET` are `{generated}`. The CLI creates each value once per Workspace and Portal with `secrets.token_urlsafe(32)`, keeps them in `$XDG_STATE_HOME/agent-sandbox/portal-secrets/<session>.json` (mode 0600, directory 0700, refused if inside the Workspace or readable by others), and prints the username and password with the URL on every `portal start`. They reach the dashboard process through `docker exec -e NAME` with the value in the docker client's environment, never on a command line, and `status`, `ls`, `check` and `up` never print them. A `login` key in a Portal entry names which two env variables are the username and password to show; project config may set it only while those variables stay `{generated}` (ADR-0005), and `{generated}` is refused for a Portal without a `command`, because the Session's environment is fixed at `up`, before any secret exists.

ADR-0010 says each Session pins its board with `HERMES_KANBAN_BOARD=<workspace slug>` and leaves open whether that stops one Workspace's dispatcher touching another's tasks in the shared Hermes Agent volume. Reading Hermes' source says it does not: the dispatcher walks every board in the Kanban home on each tick, and the variable only pins the boards that workers and CLI calls see. So the CLI does not depend on it. Each Workspace gets its own **Kanban home**: a Docker volume `agent-sandbox-kanban-<slug>`, mounted at `/kanban` with `HERMES_KANBAN_HOME=/kanban`, so no other Workspace's board exists in that volume for a dispatcher to find. `HERMES_KANBAN_BOARD=<slug>` is still set, and `up` creates that board inside the new Session (`hermes kanban boards create <slug> --name <workspace dir>`, which is a no-op for an existing board), because Hermes ignores a pinned board that does not exist. The volume is never removed by the CLI, so boards persist across Sessions. Only Hermes reads these variables; OMP and the other agents are not wired to Kanban.

## Considered Options

- **Pin `HERMES_KANBAN_BOARD` only, in the shared Hermes volume (ADR-0010 as written):** rejected. Whether it stops the dispatcher touching other boards is unverified, and the source suggests it does not; the failure would be one project's sandbox starting workers for another project's tasks.
- **Put `kanban.db` in the Workspace:** rejected. The agent could edit it, it would land in the repo, and the Workspace is the boundary for files the human cares about, not for Hermes' bookkeeping.
- **Replace the Hermes Agent volume per Workspace:** rejected. It would log Hermes out in every Workspace (ADR-0006).
- **Generate the login with a fixed or user-chosen password:** rejected. A fixed one is a published credential; a chosen one must be stored somewhere, which is the same problem.
- **Print the login in `status` and `ls` as well:** rejected. They are run more often, in shared terminals and logs; `portal start` is where the human is about to use it.

## Consequences

- One more volume per Workspace (small, kept by `asb down`; `docker volume rm agent-sandbox-kanban-<slug>` deletes the board). `check` names it.
- The agent can read the generated login (it is in the dashboard process's environment and in `/proc`), and can reach the dashboard. Accepted in ADR-0010: the dashboard only controls Hermes inside the same sandbox.
- The login is stored in plaintext in the user's state directory, readable by that user. Anything running as the user on the host can read it; it protects only a localhost port.
- The agent image now builds Hermes' web UI (it cannot be built at start with a read-only root) and installs the `[web]` extra. This makes the image build slower and larger, and ties it to Hermes' build scripts, which have no stability promise.
- Unverified, needs a spike (docs/spikes/hermes-dashboard.md): the Host-header check accepting `127.0.0.1:<random>`, Hermes honouring `HERMES_KANBAN_HOME`, the image build steps, and the login form working in a browser.
